# 3DoF 性能验证（2026-10-31）

设备：Android 显示眼镜，Android 14 / API 34，480×380。

## 项目链路

Kotlin Activity 通过 WebView 加载抖音同源页面，注入红果式播放器和手势状态机。
开启防抖时，主线程把 WebView 录制到 RenderNode，由 HardwareRenderer 输出到
SurfaceTexture；独立 GL 线程采样 OES 纹理，并用头部四元数做三轴旋转补偿。
姿态来自 100Hz Game Rotation Vector，经过相对零位和 1 Euro 滤波。

## 已确认的问题和修复

- 原始实现的到帧通知默认交给主线程。真实播放时反复出现
  `OpenGLRenderer: dequeueBuffer failed, error = -110`，并记录约 4041ms 的长帧。
  使用本次开始时保存的源码重新构建对照 APK 后，也复现相同超时。
- 到帧通知改到 GL Handler，GL 使用自己的 Choreographer 按 VSYNC 渲染，
  不再由 100Hz IMU 和视频到帧分别唤醒、交换缓冲。
- 离屏输入最多一帧待消费；若 HWUI 丢掉提交而没有到帧通知，100ms 后允许重试。
- 输出改成 SurfaceView，使显示缓冲由 SurfaceFlinger 独立消费。
  这是 Android 图形架构支持的独立合成方式，见
  [AOSP 图形架构](https://source.android.com/docs/core/graphics/architecture)。
- 后台暂停完整停止生产者、GL 和 IMU；重建时过滤旧初始化回调。
- 缓存 uniform 位置和显示旋转，复用传感器数组；滤波器重置同时清空角速度。

保持原有 480×380、1:1 画面、20° 水平视场、350ms 跟随时间常数、25°/s 速度门控。
本次未修改轴向映射或降低视频帧率。用户先反馈方向/歪斜，配合取样后再试反馈“我觉得还行”；
这不是完整的轴向标定结论，未据不充分样本交换坐标轴。

## 验证结果及边界

- 第一轮（TextureView + 调度修复）：同一视频连续 21.77s，推进 21.77s，
  浏览器统计 653 帧、丢 6 帧。
- 第二轮（SurfaceView）：同一视频连续 21.73s，推进 21.73s，
  浏览器统计 652 帧、丢 3 帧（约 0.46%）。两个轮次播放素材不同，不能把差值当作
  SurfaceView 的严格性能收益。
- GL 日志通常每约 5.03s 输出 300 帧，约 59.6fps。修复后观察窗口未再出现上述
  4 秒队列超时；浏览器丢帧统计反映视频播放，GL 日志反映提交频率，均不是光学延迟测量。
- 最终 APK 重新安装后校验设备内 APK 与本地构建 SHA-256 一致；恢复推荐流后，
  防抖开启、同一视频连续 20s，视频推进 20.008s，501 帧、丢 0 帧。
  最终安装后的首次推荐流加载曾停留等待状态，重新进入 `/home` 后恢复播放；
  未修改推荐流或签名桥代码，也未把该现象归因于 3DoF。
- 真实播放仍有开销：应用进程 CPU 抽样约 150%–160%（单核 100%，设备共四核），
  尚不能宣称降低功耗；长时间佩戴、发热降频和不同码率视频仍需持续验证。
- 连续 6 次关闭/开启成功；退后台确认管线停止，返回前台重新初始化并继续输出。
- `assembleDebug`、`testDebugUnitTest`（4 项）和 `lintDebug` 通过；Lint 仍有项目现存警告。
  滤波重置测试在原始实现上失败，修复后通过。

本次测试用 APK 与项目内已有预构建 APK 的调试签名不同。测试设备起初未安装本应用；
替换本次刚安装的对照版本前备份了应用数据，安装本机构建版本后恢复了数据。
