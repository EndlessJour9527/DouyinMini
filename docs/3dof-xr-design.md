# 无相机 3DoF 三模式、重投影和画质

测试目标为 Android 显示眼镜，不增加 CAMERA 权限，不调用相机。
测试设备支持 GLES 3.2、60Hz 显示和最高 200Hz 融合旋转向量。
仅依赖陀螺仪与加速度计即可跟踪旋转，不需要相机；本方案不提供平移补偿、环境地图、遮挡或空间重定位。

## 行为约定

1. **模式 1（默认）原始跟随**：保留修改前的 100Hz 融合姿态、1 Euro 滤波、
   350ms 跟随和 25°/s 速度门控。最终投影使用滤波姿态，不加入模式 2 的预测和角度限制。
2. **模式 2 预测跟随**：200Hz 融合姿态，最新原始姿态短时预测驱动末端重投影，
   滤波姿态驱动 250ms 平滑锚点；持续转头时加速追随，补偿偏移最多 3°。
3. **模式 3 方向锚定**：200Hz 姿态和短时预测，锚点不自动追头。
   这是会漂移的方向锚，不是位置锚、SLAM 或跨重启持久化空间锚。
4. 快捷菜单有 3DoF 开关、模式循环（1→2→3→1）和回正。
   锚定窗可能离开视野；模式 3 长按打开菜单时先回正，确保菜单能找回。
5. 模式切换、重新开启或前台恢复时，以新管线的首个有效姿态建立零位。
   原来的防抖开关保留，模式偏好另行保存；无历史偏好时默认模式 1。

原始跟随方式按用户后续要求保留为模式 1，新增预测跟随和锚定分别编号 2、3。

## 调度和姿态

- WebView 内容生产和 GL 重投影分别调度，复用最近一张有效纹理。
- 支持时以 `requestVideoFrameCallback` 通知内容更新；无新视频帧时避免整页重采样，
  仍每 100ms 刷新一次 UI，原生手势后 300ms 保持动画采样。旧 WebView 自动保留逐帧捕获。
- IMU 发布包含时间戳、原始相对姿态、滤波跟随目标的不可变快照；模式 1 为 100Hz，模式 2/3 为 200Hz。
- 模式 2/3 Warp 使用最新原始姿态；模式 2 锚点使用滤波目标，避免把旧低通姿态直接用于末端补偿。模式 1 保留旧方式。
- API 33+ 读取 Choreographer preferred frame timeline 的预计呈现时刻，
  旧系统保留 frame callback 和显示周期估计；两种时钟明确转换后才预测。
- 短期恒角速度预测最多 30ms、最多 3°；超过 50ms 的陈旧采样、乱序和异常采样不外推。
- GL 和 IMU 使用普通 Android 显示线程优先级，不申请实时调度权限。
- 应用层不控制 HWC/扫描线，无实时调度优先级保证，不宣称系统级 ATW 或零光学延迟。
- 保留原来的 20° 水平投影视场假设，未进行光学视场/畸变标定；数字截图和 GL 日志不能证明光学误差已消除。

参考：[Meta ATW](https://developers.meta.com/vr/blog/asynchronous-timewarp-examined/)、
[OpenXR 帧提交](https://github.com/KhronosGroup/OpenXR-Guide/blob/main/chapters/frame_submission.md)、
[Android FrameTimeline](https://developer.android.com/reference/android/view/Choreographer.FrameTimeline)、
[Game Rotation Vector](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position)。

## 清晰度

原播放器硬性排除高于 540P 的源，同档码率升序且把重定向地址整体提前。
先提高到最高 1080P 的 H.264 优先选源、高码率优先、逐地址保留降级顺序，继续排除独立 DASH 视频源。
不修改视场和画面大小，不用放大裁切伪装提升分辨率；显示面板实际仍为 480×380。
重投影的二次插值另行测量，画质收益不能由分辨率标签替代。

## 验证和边界

- 纯 Kotlin 测试：预测方向、时钟/陈旧样本/速度上限、跟随和锚定、回正与切模式。
- Node 测试：真实选源函数对 1080/720/540、高低码率、H.264、DASH 和 CDN 地址的顺序。
- 选源测试：`node --test tests/video-source.test.cjs`。
- 构建：`./gradlew assembleDebug testDebugUnitTest lintDebug`。
- 设备：核对实际采样率、GL 帧率、选中视频实际尺寸和丢帧；暂停、开关、重启；
  确认无相机权限和使用记录。佩戴手感与光学清晰度需用户复测，截图只代表数字管线。

## 完整画质优化开关

快捷菜单「画质优化」，默认开启并持久化；与三种跟随模式独立。

| 项目 | 开启 | 关闭（画质优化前配置） |
| --- | --- | --- |
| 选源上限 | 1080P | 540P |
| 码率和 CDN 顺序 | H.264 优先、高清/高码率优先，按画质分组降级 | 原始排序：H.264、分辨率降序、码率升序；全局重定向地址优先 |
| 离屏捕获 | 720×570 | 480×380 |
| 投影边界 | 约一个输出像素的覆盖抗锯齿、不透明黑边 | 原始硬裁切及透明黑边 |

全部画质修改均由该开关控制。两档共用独立重投影、帧流控、视频帧驱动捕获、
`CaptureWebView` 去重复绘制、生命周期和资源释放优化；不切换跟随模式。
这是画质配置对照，不回退性能实现或三模式实现。

切换会短暂重新加载同一视频，保留播放位置、暂停状态、倍速和当前模式。
每个正常化视频项保留两套选源列表；换档同步更新队列、待播放项并清空预加载。
缺少档位信息的旧历史/收藏 URL 不直接复用，而是重新解析元数据；异步旧响应通过版本号丢弃。
若当前视频没有对应档位，提示源不可用，不偷偷继续使用高清源冒充原始画质。

选源开关在关闭 3DoF 时仍生效；捕获分辨率和投影边界仅在 3DoF 开启时生效。
切换 GL 捕获尺寸时先发布新缓冲尺寸再放开生产者流控，避免错尺寸过渡帧。
增强分支在裁剪前计算片段导数，原始分支保留修改前的采样/裁剪公式。

用户确认 1080P 选源后更清晰，第一版超采样/边界抗锯齿反馈为“仍会闪，但有所减轻”。
不能据此宣称闪烁完全消失；完整开关方便佩戴后进一步同片比较。

完整开关的设备验证：同一视频在 1920×1080 和 960×540 间往返切换，
暂停位置 117.995841s 在两档间保持不变，暂停状态也保持；GL 日志确认增强捕获
720×570、原始捕获 480×380。设备测试过程中用户另外操作了模式，因此不把整段测试
记录的模式变化归因于画质开关。
8 项 Node 测试覆盖原始顺序、缓存失效、暂停位置记录及连续切换的过期响应丢弃；
14 项 Kotlin 测试、构建和 Lint 通过。

## 设备验证（2026-10-31）

关闭 Android Studio 镜像后，同一条 1920×1080 视频，三模式各测 20 秒：

| 模式 | 实际推进 | 视频帧数 | 浏览器丢帧 |
| --- | ---: | ---: | ---: |
| 1 原始跟随 | 20.006s | 601 | 3 |
| 2 预测跟随 | 20.003s | 601 | 5 |
| 3 方向锚定 | 20.013s | 601 | 3 |

GL 约 59–60fps；输入捕获通常约 28–30fps。视频统计与 GL 提交统计不是光学延迟测量。
模式菜单实测完成 1→2→3→1；偏好存储验证通过。无 CAMERA 权限，AppOps 没有相机调用记录。
14 项 Kotlin 测试、3 项 Node 选源测试、构建和 Lint 通过；保留项目已有警告。

### 性能和温度证据边界

- 测试设备的 ThermalService 只给出固定 30°C 的 `test sensor`，不可用作真实温升结论。
  本次改读 `/sys/class/thermal/thermal_zone*/type,temp` 的 CPU、GPU、video、系统热敏和电池节点。
  这些是内部传感器值，不能等同镜腿接触皮肤的表面温度。
- 真实使用中 CPU 节点约 56–61°C，GPU 约 54–59°C，电池约 33–35°C；设备 USB 供电，
  不能用这些读数换算独立电池续航或实际耗电瓦数。
- 超采样版本采用 `CaptureWebView`，保持 Chromium 附着和可见，只把内容画到捕获表面，
  跳过窗口中的重复绘制。Perfetto 中原来的 `drawLayer [WebView]` 路径不再出现。
- 同一视频的初步可比区间，应用进程 CPU 从约 144% 降到约 115%（100%=一核）。
  这是短样本；后续体验包含切视频、切模式和关闭防抖，不可把混合样本的降温全部归因于优化。
- 用户选择先继续体验，固定模式、固定视频的 10 分钟温升测试暂缓。尚不能宣称长时间温升已解决，
  也不能仅凭重启后较低的 PSS 证明没有长期内存增长。
